Transport Layer — The STDIO Foundation

MCP communicates over standard I/O streams by default. The host process starts your server as a subprocess and communicates through stdin/stdout. Every message is a single JSON line.

Critical Rule: Never write anything to System.out except JSON-RPC messages. All debugging and logging must go to a file. Writing non-JSON to stdout breaks the protocol connection immediately.

IOHandler — The Communication Hub

The IOHandlerImpl class manages all I/O with three responsibilities:

📥 Input Reading

public void startInputReader() {
    Scanner scanner = new Scanner(System.in);
    running.set(true);
    while (running.get()) {
        if (!scanner.hasNextLine()) {
            running.set(false); break;
        }
        String line = scanner.nextLine();
        logger.log("[API][RECEIVED]" + line);
        publishLine(line); // → listeners
    }
}

A blocking read loop — Server.start() calls it on the main thread after registering the router as a listener. Publishes each JSON line to all registered listeners via the Observer pattern.

📤 Output Emission

public void emit(Object message) {
    String text = gson.toJson(message);
    logger.log("[API][SENT]: " + text);
    writer.println(text);
    writer.flush(); // immediate
}

Serializes any Java object to JSON via Gson. Immediately flushes — MCP clients expect real-time responses.

Key Design Choices

  • CopyOnWriteArrayList for thread-safe listener management
  • AtomicBoolean for safe running-state across threads
  • Process-specific log files using PID — no conflicts when multiple servers run
  • Router interface — the IOHandler doesn't know what messages mean, it just moves them
Chapter 2

JSON-RPC 2.0 — The Message Protocol

MCP uses JSON-RPC 2.0 as its wire format. Every message is a JSON object with a defined structure. There are four message types:

Request

Client or Server → Other Side

{
  "jsonrpc": "2.0",
  "id": 6,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion":
        "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

Has an id — expects a Response back with the same id, in the same type. Ids may be strings or numbers.

Response

Other Side → Requester

{
  "jsonrpc": "2.0",
  "id": 6,
  "result": {
    "resultType": "complete",
    "tools": [{
      "name": "key_word_search",
      "description": "..."
    }],
    "ttlMs": 60000,
    "cacheScope": "public"
  }
}

Returns result with the same id. Every result carries resultType; cacheable ones also carry ttlMs and cacheScope.

Notification

Either Side → Other Side

{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": "listen:0",
    "reason": "user navigated away"
  }
}

No id — fire-and-forget. No Response expected. This is the only message shape a server may send unprompted.

Error Response

Server → Client (on failure)

{
  "jsonrpc": "2.0",
  "id": 7,
  "error": {
    "code": -32601,
    "message": "Method not found: initialize"
  }
}

Standard codes: -32700 Parse Error, -32600 Invalid Request, -32601 Method Not Found, -32602 Invalid Params. MCP adds -32021 and -32022 in the reserved -32020..-32099 band.

The Fourth Shape That No Longer Exists

JSON-RPC is symmetric: either party may send a Request. MCP used that symmetry until revision 2026-07-28 — the server would send roots/list or elicitation/create to the client. Modern clients silently discard inbound requests. A server now has exactly two things it may put on the wire: a response to something it was asked, and a notification. Everything else — including questions — has to fit inside a response. That constraint is what the Extensions chapter is about.

MCP Method Namespace

All MCP methods follow a category/action naming convention:

server/discover

Versions, capabilities, identity — creates no session

resources/*

list, read — discover and fetch content

tools/*

list, call — discover and execute tools

prompts/*

list, get — discover and fetch templates

tasks/*

get, update, cancel — long-running work

subscriptions/*

listen — one request carrying every server push

Three namespaces are conspicuously absent from that grid, and their absence is the shape of the revision. roots/*, sampling/*, and elicitation/* are no longer methods you can send anywhere: they exist only embedded inside a result. Send one to this server and you get -32601, the same as any deleted method.

Stateless by Design — Now Literally

This slide used to carry an asterisk. The server held no application state between calls, but it did hold a session: a negotiated protocol version, a capability set, a roots list, sometimes a half-finished tool call. Revision 2026-07-28 removed the asterisk by removing the session.

  • Any request can arrive in any order — there is no "after initialization" any more, because there is no initialization
  • Servers scale horizontally — every request is self-describing, so any instance behind a load balancer can serve any request; no sticky routing, no shared session store
  • Results become cacheable — a self-describing request has a stable identity, which is why ttlMs and cacheScope could be added at all
  • Debugging is simpler — one captured line is a complete, replayable request

Nothing is free. The cost is paid twice over: the server cannot send a request, and it cannot remember a half-finished one. Chapters 5 and 7 are, between them, the bill.

Capability-Based Feature Detection

Both sides still declare what they support; what changed is when. The server declares once, in the server/discover result, and the client may cache it. The client declares on every single request, in the _meta envelope — because the server has nowhere to write it down.

The effect is the same: a server may only embed an elicitation/create if this request's envelope declared elicitation, and may only hand back a task if this request's envelope declared the tasks extension. No guessing — explicit opt-in, restated every time.

Chapter 1 Live: The Transport Layer in Code

Switch to the IDE. Have lessons/01-instructions.md open in a side tab — it is the script for this demo. You are on the complete branch, so everything already works; narrate each block as the lesson presents it.

  1. Open src/main/java/com/workshop/mcp/io/IOHandlerImpl.java — this class is the entire transport layer. Point out the collaborators at the top: the auto-flush PrintWriter over System.out, the running AtomicBoolean, the lineListeners CopyOnWriteArrayList, and the Gson instance.
  2. Walk startInputReader() — the Scanner loop over System.in. Trace the happy path: hasNextLine() → nextLine() → log [API][RECEIVED] → publishLine(line). Then trace the shutdown path: stream closes → running.set(false) → stopRunning() in the finally block.
  3. Walk publishLine() — the observer pattern in six lines. Each listener call is wrapped in its own try-catch so one faulty listener never breaks the others. The router registers itself as a listener; the transport never knows what messages mean.
  4. Walk emit() — gson.toJson(), log [API][SENT], println, explicit flush(). Emphasize the flush: MCP clients expect real-time line-delimited responses.
  5. Open LogFileWriter.java — show that all logging goes to a PID-named file, never stdout. Reinforce the critical rule from the card above: stdout is protocol-only.
  6. Build and test: in the terminal run ./gradlew clean build. Open IOHandlerImplTest.java and show the tests exercising the reader loop and emit path passing.
  7. Prove it end to end: run java -jar build/libs/agent-mcp-workshop-0.0.1.jar, paste a raw JSON-RPC line (e.g. a ping request) into stdin, and show the JSON response come back on stdout plus both [API][RECEIVED] and [API][SENT] entries in the log file.

What the audience should observe: the transport is dumb on purpose — it moves lines and knows nothing about MCP. Everything protocol-aware lives behind the listener boundary. Next we look at what those lines contain: JSON-RPC 2.0, then the full session flow on the Flow Diagram.
