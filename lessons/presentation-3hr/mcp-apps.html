What Are MCP Apps?

Text responses can only go so far. MCP Apps let your server return an interactive HTML interface that renders directly inside the conversation — right next to the chat that triggered it.

❌ Without MCP Apps

User asks → LLM calls tool → Returns wall of text:

/path/api.http, keyword_count=1
/path/README.md, keyword_count=3
/path/pom.xml, keyword_count=2
... 55 more files

Hard to explore, no interactivity, no visualization

✅ With MCP Apps

User asks → LLM calls tool → Interactive dashboard appears inline:

🔍 Keyword Search Results
Found 58 files • 400+ matches
api.http ×1 README.md ×3 pom.xml ×2
[ Search Again ] [ Filter ] [ Export ]

Sortable, filterable, interactive — stays in context

The tool continues to work exactly as before. The only addition is a _meta field in the tool definition that points the host to an HTML resource to render alongside the tool result.

What You Add to the Protocol

1. Declare the extension in server/discover

{
  "capabilities": {
    "extensions": {
      "io.modelcontextprotocol/ui": {
        "mimeTypes": ["text/html;profile=mcp-app"]
      }
    }
  }
}

On revision 2026-07-28 this moved out of the experimental map into the dedicated extensions slot, and the identifier is io.modelcontextprotocol/ui. The declaration also names the mime types the server can serve, so a host knows before fetching anything whether it can render what is on offer. Clients read this from the server/discover result and cache it; if the extension is absent, the app never appears and the tool still works normally.

2. Add _meta to your tool definition — under both keys

{
  "name": "key_word_search",
  "description": "Searches for a keyword across all project files.",
  "inputSchema": { "...": "..." },
  "_meta": {
    "ui": {
      "resourceUri": "ui://keyword-search/mcp-app.html"
    },
    "ui/resourceUri": "ui://keyword-search/mcp-app.html"
  }
}
Yes, the same URI twice. The nested _meta.ui.resourceUri is the original shape; the flat _meta["ui/resourceUri"] is the one the revision standardised on, matching how every other _meta member is a slash-namespaced flat key. Hosts in the wild currently read one or the other, so a server that wants to be rendered by both emits both. They must always agree.

This is transitional, and worth telling the class as much: the flat key is where the spec is going and the nested one is politeness toward hosts that have not caught up. Emitting both costs a few bytes on a cacheable result. Emitting only the nested one costs you the newer hosts.

3. Serve the HTML when the host requests it

// In your resources/read handler:
if (uri.startsWith("ui://")) {
    // Return the bundled HTML
    return new ResourceContent(uri,
        "text/html;profile=mcp-app",
        readHtmlFromClasspath("mcp-app.html"));
}

The MIME type text/html;profile=mcp-app tells the host this is an MCP App, not a regular HTML resource — the same string the extension declared in mimeTypes, which is what lets the host decide up front whether it can render this at all.

One detail from the wider revision applies here: resources/read is one of the five cacheable methods, so the result also carries resultType, ttlMs, and cacheScope. An app's HTML is exactly the kind of thing you want a host to fetch once and keep.

How It Works: Step by Step

1

User asks a question

"Show me keyword search results for 'mcp'"

2

Host calls tools/list

Sees key_word_search carries a UI resource uri in _meta — under whichever of the two keys it happens to read. Preloads the UI resource. Note the result is cacheable, so on a warm host this step may not hit the wire at all.

3

Host fetches resources/read ui://keyword-search/mcp-app.html

Server returns the HTML page. Host prepares the sandboxed iframe.

4

LLM calls tools/call key_word_search

Server returns the matching file list as text content.

5

Host renders HTML + pushes tool result

The iframe appears inline in the conversation. The app receives the tool result via postMessage and updates its UI.

6

User clicks "Search Again"

The app calls back through postMessage → host routes → tools/call → fresh results → UI updates. No page reload, no context switch.

The Three New Java Types

UiMeta

Holds the resourceUri pointing to the HTML resource at the ui:// URI. This is the nested half of the pair.

AppMeta

The _meta object on a tool definition. Carries UiMeta as ui and the flat ui/resourceUri string, kept in sync by construction so the two can never disagree.

AppTool + AppToolBuilder

A tool record with name, description, inputSchema, and _meta — and, as of this revision, no execution field. Fluent builder for construction.

Tool.execution is gone. Tools used to advertise execution: { "taskSupport": "optional" } so a client could tell whether it was allowed to task-augment the call. That hint was removed on 2026-07-28, and clients strip it silently if they see it.

The reason is a round trip. Because the hint lived in tools/list, a client had to fetch the tool list before it could safely make any call — a mandatory warm-up in service of a decision the client no longer gets to make, now that the server decides when to return a task. Removing it lets a client that already knows a tool's name call it cold. It also means an AppTool is now purely name, schema, and presentation.

Security Model — Sandboxed Iframes

🚫 Cannot access parent DOM

The app runs in a sandbox. It cannot read or modify the host page.

🚫 Cannot read cookies

No access to the host's cookies or local storage.

🚫 Cannot navigate parent

The app cannot redirect the conversation or navigate away.

✅ Controlled postMessage

All communication goes through a strict JSON-RPC postMessage channel managed by the host.

Hosts can safely render third-party MCP Apps without fully trusting the server author.

When to Use MCP Apps

✅ Good Fit

  • Exploring complex data (tables, charts, maps)
  • Configuring with many options (forms)
  • Rich media (PDF viewers, image galleries)
  • Real-time monitoring dashboards
  • Multi-step workflows with approve/reject

❌ Not Needed

  • Simple text responses
  • Single-value lookups
  • Linear workflows with no branching
  • Cases where a list or table in markdown is sufficient

Chapter 6 Live: The Keyword Search Dashboard

Switch to the IDE with lessons/06-instructions.md open as the script.

  1. Open the three spec records in src/main/java/com/workshop/mcp/spec/ — UiMeta (just a resourceUri), AppMeta (which emits it twice, nested as ui and flat as ui/resourceUri), and AppTool. Ask the class to spot the duplication before you explain it; someone always assumes it is a bug.
  2. Show AppToolBuilder in spec/builders/ — the same fluent pattern as every other builder, plus withResourceUri("ui://keyword-search/mcp-app.html"). One call, both keys: the duplication is impossible to get wrong from the outside.
  3. Point at what is missing from AppTool — there is no execution field any more. Tie it back to Ch 7: the client no longer decides about tasks, so the hint that fed that decision went with it.
  4. Open lessons/mcp-app.html directly in the browser — the standalone dashboard with mock data. Point at the comments explaining where app.ontoolresult and app.callServerTool take over in a real host.
  5. Walk the four IORouter changes: the io.modelcontextprotocol/ui extension declared with its mimeTypes in server/discover, AppToolsListResult from TOOLS_LIST, the ui:// resource added in RESOURCES_LIST, and the ui:// branch in RESOURCES_READ serving the HTML with MIME type text/html;profile=mcp-app.
  6. In Inspector — Tools tab: open the raw JSON for key_word_search and show both _meta keys side by side. Resources tab: ui://keyword-search/mcp-app.html appears; read it and show the MIME type matching the declared one exactly.
  7. Apps tab: click Refresh Apps — Keyword Search App appears. Run a search from inside the rendered dashboard and watch the tool round-trip happen from the iframe.

What the audience should observe: MCP Apps are still just a tool plus a resource plus _meta — no new protocol machinery, and the statelessness migration barely touched them. What did change is bookkeeping: a different extension slot, a second copy of the uri, and one field fewer on the tool. Hosts that don't support Apps ignore _meta and the tool keeps working as text.
