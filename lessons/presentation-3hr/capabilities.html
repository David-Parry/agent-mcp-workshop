Discovery, the _meta Envelope & Routing

Revision 2026-07-28 deleted the initialize handshake. There is no longer a moment where the two sides agree once on a version and exchange capabilities. Instead there are two separate mechanisms, and it is worth being precise about which is which:

  • server/discover is where a client learns the server's capabilities. It creates nothing — no session, no state — so the server can answer it from static configuration, and the client can cache the answer.
  • The _meta envelope is where the server learns the client's capabilities. It rides on every single request, not once at startup, because there is nowhere to remember it between calls.

server/discover (Client → Server)

{
  "jsonrpc": "2.0",
  "id": "server-discover-probe-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion":
        "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "inspector-cli",
        "version": "2.5.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {
        "roots": { "listChanged": true },
        "extensions": {
          "io.modelcontextprotocol/tasks": {},
          "io.modelcontextprotocol/ui": {
            "mimeTypes": ["text/html;profile=mcp-app"]
          }
        }
      }
    }
  }
}

Note the string id. Ids may be strings or numbers on this revision and the server must echo back the exact form it received — see the String or Number card below.

server/discover result (Server → Client)

{
  "jsonrpc": "2.0",
  "id": "server-discover-probe-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "completions": {},
      "prompts": { "listChanged": false },
      "resources": {
        "listChanged": false,
        "subscribe": false
      },
      "tools": { "listChanged": false },
      "extensions": {
        "io.modelcontextprotocol/ui": {
          "mimeTypes": ["text/html;profile=mcp-app"]
        },
        "io.modelcontextprotocol/tasks": {}
      }
    },
    "instructions": "Searches a project for …",
    "ttlMs": 60000,
    "cacheScope": "public",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "agent-mcp-workshop",
        "version": "0.0.1"
      }
    }
  }
}

Two things moved. There is no single protocolVersion — the server lists supportedVersions and the client picks. And serverInfo is no longer a body field; it lives in _meta.

Why delete the handshake at all?

A session is memory pinned to one process, and pinned memory is the thing that stops you scaling. With the handshake gone:

  • Horizontal scaling. Any instance behind a load balancer can answer any request, because every request is self-describing. No sticky sessions, no shared session store, no reconnection dance after a deploy.
  • Caching. A self-describing request has a stable identity, so its response can be cached and replayed. That is exactly why ttlMs and cacheScope exist on this revision — they are only meaningful once a result no longer depends on hidden session state.
  • Debuggability. One captured line is a complete, replayable request. You can paste it into a terminal and get the same answer.

The bill for all that comes due in two places, and the rest of this deck is largely about paying it: the server can no longer send a request to the client (see Extensions), and it can no longer remember a half-finished operation (see requestState, same page).

The Envelope, Field by Field

Everything below lives under params._meta on every request.

KeyRequired?What it does
io.modelcontextprotocol/protocolVersionRequiredThe revision this request speaks. A value the server does not implement is -32022.
io.modelcontextprotocol/clientCapabilitiesRequiredWhat the client can be asked to do on this request. This is what gates whether the server may embed a roots/list, show a form, or hand back a task.
io.modelcontextprotocol/clientInfoRecommendedWhich client software is calling. Useful for logs and workarounds; nothing depends on it.
io.modelcontextprotocol/logLevelOptionalOpt-in to notifications/message for this request. When it is absent the server MUST NOT emit any — silence is the default, not a level.

Missing either required member is -32602. Declaring an unsupported revision is -32022, and its data carries both supported and requested so the client can renegotiate from the error alone. If a server needs a capability the request did not declare, that is -32021 with data.requiredCapabilities.

The Error Code Table

This revision partitioned the JSON-RPC server-error range. -32000–-32019 stays implementation-defined; -32020–-32099 is now reserved for the specification, so do not squat on it.

CodeMeaningWhen this server emits it
-32700Parse errorUnparseable JSON on stdin.
-32600Invalid requestValid JSON that is not a JSON-RPC message.
-32601Method not foundAny method this revision removed, and the three embedded-only methods.
-32602Invalid paramsMissing envelope members; an unknown taskId.
-32603Internal errorRegistered method with no handler — unreachable by construction.
-32020Header/body mismatchNever. Streamable HTTP only, so a stdio server cannot emit it.
-32021Missing required client capabilitydata.requiredCapabilities is an object shaped like ClientCapabilities — never an array.
-32022Unsupported protocol versiondata.supported + data.requested, both required.

What Was Deleted — and How Deletion Works Now

Deletion in this revision is physical: the method is simply absent from the registry, so it answers -32601 by absence rather than by a special case. These are gone:

initialize                        notifications/initialized
ping                              notifications/roots/list_changed
logging/setLevel                  resources/subscribe
tasks/result                      resources/unsubscribe
tasks/list

One ordering detail matters for diagnosis: the server settles method existence before it validates _meta. A legacy client sending initialize is told the method is gone, not that its envelope is malformed — which is the difference between a five-second fix and an afternoon.

Message Routing — The IORouter Switch

Every request is routed on its method name, but only after two gates: discovery is answered first (asking which versions a server speaks cannot itself require knowing them), then method existence, then the envelope.

SERVER_DISCOVER          → answered first, before any version check
─── if the method is not in INBOUND_METHODS → -32601 ───
─── envelopeFor(message): -32602 or -32022, or the validated envelope ───
case PROMPTS_LIST        → cacheable: + ttlMs, cacheScope
case PROMPTS_GET         → resultType only
case TOOLS_LIST          → cacheable
case TOOLS_CALL          → complete | input_required | task
case RESOURCES_LIST      → cacheable
case RESOURCES_TEMPLATES_LIST → cacheable (answered even when empty)
case RESOURCES_READ      → cacheable
case COMPLETION_COMPLETE → resultType only
case SUBSCRIPTIONS_LISTEN→ acknowledge by notification, not by result
case TASKS_GET / TASKS_UPDATE / TASKS_CANCEL → tasks extension

Two Rules About Results

resultType is required on every result

Three values only: "complete", "input_required", "task". It is how a client knows whether it is holding an answer, a question, or a receipt — without inspecting the shape.

ttlMs + cacheScope on exactly five methods

tools/list, prompts/list, resources/list, resources/templates/list, resources/read. ttlMs is non-negative; cacheScope is "public" or "private". Their neighbours — prompts/get, tools/call, completion/complete — must not carry them, because their answers depend on arguments.

String or Number — Why RequestId Exists

JSON-RPC has always allowed either, but clients now genuinely mix both on one connection. The Inspector uses the string "server-discover-probe-1" to discover, "listen:0" to subscribe, "inspector-ext-1"…"inspector-ext-4" to poll a task, and plain integers for everything else. A server must echo the id back in the form it arrived.

Before the migration this server typed id as Long and died on the very first message with NumberFormatException: For input string: "server-discover-probe-1". That is what spec/RequestId.java and spec/RequestIdTypeAdapter.java are for: one record holding either form, and a Gson adapter that serializes it back as whatever it was.

Server Capabilities — Exactly Seven Slots

The capability object is now fixed at seven optional slots. Anything outside them, tasks included, belongs under extensions.

SlotMeaning
experimentalNon-standard capabilities, keyed by name.
loggingPresent when the server can emit notifications/message.
completionsPresent when the server answers completion/complete.
promptsOptionally listChanged.
resourcesOptionally listChanged and subscribe.
toolsOptionally listChanged.
extensionsExtension declarations, keyed by identifier — this is where io.modelcontextprotocol/tasks and io.modelcontextprotocol/ui live.

Two survivals worth explaining, because both look like oversights and neither is. resources.subscribe outlived the resources/subscribe method — it now gates the resourceSubscriptions field of subscriptions/listen. And this server declares listChanged: false everywhere on purpose: its lists are fixed, and advertising true would invite clients to hold a subscription open for notifications that will never come.

STDIO Discipline

  • All logs go to logs/agent-mcp-workshop-<pid>-<timestamp>.log (relative to the server's working directory — inspector/logs/ when launched by the Inspector) — never to System.out
  • Writing non-JSON to stdout breaks the protocol immediately
  • The client reads stdout byte-by-byte looking for newline-delimited JSON
  • With the handshake gone, stdout also carries interleaved traffic that is not a reply to anything: notifications/tasks while a task runs, and any subscription notification. Correlation is by id or by _meta, never by arrival order.

Resources — Serving Content from the Server

Resources allow the server to expose any content the client can discover and read. Our server exposes 70+ Javadoc HTML files bundled inside the JAR.

resources/list — Discovery

Returns a paginated list of all available resources with URI, name, description, and MIME type — plus the freshness hints that make it cacheable:

{
  "resultType": "complete",
  "resources": [{
    "uri": "javadoc/com/workshop/mcp/spec/Capability.html",
    "name": "Capability",
    "description": "Represents the capability...",
    "mimeType": "text/html"
  }],
  "nextCursor": "pageNext",
  "ttlMs": 60000,
  "cacheScope": "public"
}

resources/read — Retrieval

Returns the actual content of a specific resource by URI. Also cacheable, so also carries the hints:

{
  "resultType": "complete",
  "contents": [{
    "uri": "javadoc/...",
    "mimeType": "text/html",
    "text": "..."
  }],
  "isError": false,
  "ttlMs": 60000,
  "cacheScope": "public"
}

resources/templates/list — Newly Load-Bearing

This method has been in the spec for a while, but on 2026-07-28 clients fetch it whenever a server declares any resource capability at all. It is no longer optional to answer, even if you expose no templates:

{"resultType":"complete","resourceTemplates":[],"ttlMs":60000,"cacheScope":"public"}

Leaving it unhandled is a popular way to hang a client that is waiting on it before it will render your resource list.

JavadocResources — Classpath Loading

  • HTML Javadoc files are bundled inside the JAR via Gradle resources
  • JSoup parses the HTML to extract documentation summaries for descriptions
  • File paths become resource URIs: javadoc/com/workshop/mcp/spec/Capability.html
  • Making the server self-contained — no external files required

Tools — Executable Functionality

Tools are functions the LLM can call. Defined with JSON Schema for parameter validation, they are the primary integration point between the LLM and your business logic.

tools/list — Discovery

{
  "resultType": "complete",
  "tools": [{
    "name": "key_word_search",
    "description": "Searches for a keyword across all files in a project.",
    "inputSchema": {
      "type": "object",
      "properties": {
        "keyword": {
          "type": "string",
          "description": "keyword to search for"
        }
      },
      "required": ["keyword"]
    }
  }],
  "ttlMs": 60000,
  "cacheScope": "public"
}

The directory is not a tool param — the server asks for it over a Multi Round-Trip Request. Note what is gone: execution.taskSupport was removed from tools/list on this revision, and clients strip it silently. On the complete branch the entry also carries the Ch 6 _meta block.

tools/call — Execution

{
  "method": "tools/call",
  "params": {
    "_meta": { … the envelope … },
    "name": "key_word_search",
    "arguments": {
      "keyword": "record"
    }
  }
}

// Response — one of three resultTypes
{
  "resultType": "complete",
  "content": [{
    "type": "text",
    "text": "/path/api.http, keyword_count=1"
  }],
  "isError": false
}

No ttlMs/cacheScope here — the answer depends on the arguments, so it is not cacheable. The other two resultTypes, input_required and task, are covered on Extensions and Tasks.

KeyWordSearch Implementation

  • Walks the directory tree recursively from each root supplied on the call
  • Roots arrive in an inputResponses answer to an embedded roots/list, or from the elicitation fallback in Ch 5 — never as a tool parameter, and never from server memory
  • Counts occurrences of keyword per file (case-insensitive)
  • Returns one text content item per matching file with its count
  • The JSON Schema required array enables client-side validation before the request is even sent

Prompts — User-Friendly Templates

Prompts are reusable templates that guide users and clients in composing effective tool calls. They appear as autocomplete suggestions in MCP-compatible clients.

prompts/list — Discovery

Cacheable, so it carries the hints:

{
  "resultType": "complete",
  "prompts": [{
    "name": "search_keyword",
    "description": "Creates a prompt to search for a word using the key_word_search tool.",
    "arguments": [{
      "name": "keyword",
      "description": "The word to search for",
      "required": true
    }]
  }],
  "nextCursor": "nextPage",
  "ttlMs": 60000,
  "cacheScope": "public"
}

prompts/get — Execution

Not cacheable — its answer folds in the arguments — so no hints:

{
  "method": "prompts/get",
  "params": {
    "_meta": { … the envelope … },
    "name": "search_keyword",
    "arguments": { "keyword": "mcp" }
  }
}

// Response
{
  "resultType": "complete",
  "description": "keyword",
  "messages": [{
    "role": "user",
    "content": {
      "type": "text",
      "text": "Start from the root of the project and use the key_word_search tool to search for this specific keyword: 'mcp'"
    }
  }]
}

The list / get split is now a caching boundary

It is worth pausing on the pair above, because the rule is easy to state and easy to get wrong. prompts/list is the same for every caller, so it is cacheable. prompts/get depends on the arguments, so it is not — and a server that attaches ttlMs to it is inviting a client to serve one user's answer to another. The same line runs between tools/list and tools/call, and between resources/list and completion/complete.
