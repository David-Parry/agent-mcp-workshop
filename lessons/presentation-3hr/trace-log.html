What a Legacy Client Sees

Three rejections worth showing side by side, because each one fails for a different reason and each one is diagnosable from the error alone.

--> {"jsonrpc":"2.0","id":4,"method":"initialize","params":{ …envelope… }}
<-- {"jsonrpc":"2.0","id":4,"error":{"code":-32601,"message":"Method not found: initialize"}}
    The method is gone, full stop. Note the server settles method existence BEFORE it
    validates _meta, so a legacy client is told the truth instead of being sent chasing
    an envelope problem it does not have.

--> {"jsonrpc":"2.0","id":5,"method":"tools/list","params":{"_meta":{
      "io.modelcontextprotocol/protocolVersion":"2025-11-25",
      "io.modelcontextprotocol/clientCapabilities":{}}}}
<-- {"jsonrpc":"2.0","id":5,"error":{"code":-32022,"message":"Unsupported protocol version",
      "data":{"requested":"2025-11-25","supported":["2026-07-28"]}}}
    The method exists; the revision does not. The data block is required — it is the only
    thing that lets a client renegotiate without a second round trip.

--> {"jsonrpc":"2.0","id":6,"method":"tools/list","params":{}}
<-- {"jsonrpc":"2.0","id":6,"error":{"code":-32602,"message":"Requests must carry
      io.modelcontextprotocol/protocolVersion and
      io.modelcontextprotocol/clientCapabilities in params._meta"}}
    No envelope at all. On the old revision this request was perfectly legal, because the
    handshake had already said all of this once.
