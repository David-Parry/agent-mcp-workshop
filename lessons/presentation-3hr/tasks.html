Chapter 7 Extension — io.modelcontextprotocol/tasks

The Problem Tasks Solve

The synchronous tools/call shape works fine for fast operations — sub-second searches, lookups, small computations. It falls apart for anything that takes longer than a polite roundtrip: large-scale processing, batch jobs, ML inference, external API calls with retries.

Tasks split a request into two trips: the receiver immediately acknowledges with a taskId and a status of working, runs the work in the background, and lets the requestor poll or cancel on its own schedule.

What Changes vs. Plain tools/call

ConcernWithout TasksWith Tasks
Long operationsHold the connection openAcknowledge fast, poll later
Crash recoveryResult lost when stream dropsRetrievable until TTL expires
Concurrent workOne slow call blocks the LLMLLM dispatches and continues
Stateless HTTPNeeds SSE or webhooksJust request/response polling
What changed on 2026-07-28. Tasks were reshaped more than any other part of the protocol. In one list: the top-level tasks capability slot became the io.modelcontextprotocol/tasks extension; tasks/result and tasks/list were removed; tasks/update was added; ttl/pollInterval became ttlMs/pollIntervalMs; notifications/tasks/status became the bare notifications/tasks; and the client no longer decides when a task is created. Each of those has a reason, and the rest of this page is those reasons.

Declaring the Extension

The nested tasks capability — with its list, cancel, and requests sub-maps naming which request categories could be augmented — is gone. Both sides now simply declare the extension by identifier. Empty {} markers are intentional: presence is the signal.

Server declares (in the server/discover result)

{
  "capabilities": {
    "tools": { "listChanged": false },
    "extensions": {
      "io.modelcontextprotocol/tasks": {}
    }
  }
}

Note there is no tasks slot beside tools. The capability object is closed at seven members and tasks is not one of them.

Client declares (in _meta, on every request)

"_meta": {
  "io.modelcontextprotocol/clientCapabilities": {
    "extensions": {
      "io.modelcontextprotocol/tasks": {}
    }
  }
}

Restated per request. A client that omits it on this call must not be handed a task on this call, whatever it said a moment ago.

Who Decides? The Server Now.

The old design let the requestor opt in per call, by attaching params.task = { ttl: 60000 }. That field is removed, and servers must ignore it if a legacy client sends one.

The reasoning is that the requestor is the party least able to judge. Whether a keyword search across a monorepo takes eight milliseconds or eight minutes is knowable only on the server side — and the client has to commit before it could possibly find out. So the decision moved to where the information is: the server returns resultType: "task" when it judges the work long enough to warrant one, and resultType: "complete" when it does not.

The client's only lever is its capability declaration. Declare the extension and you may receive a task; omit it and you may not, so the server must either run the work synchronously or fail. It is a yes/no, not a per-call instruction.

And Tool.execution Went With It

The per-tool execution.taskSupport hint ("required" / "optional" / "forbidden") was removed from tools/list at the same time, for a related but distinct reason: it forced clients to fetch tools/list before they could safely make any call, purely to learn whether augmenting it was permitted. That is a mandatory warm-up round trip in service of a decision the client no longer makes. Modern clients strip the field silently if a server still sends it.

The Task Lifecycle

Tasks are state machines with three terminal states. Receivers are forbidden from moving a terminal task back into working.

                [*]
                 │
                 ▼
        ┌────────────────┐
        │    working     │◄─────┐
        └────────────────┘      │
            │      │            │
            ▼      ▼            │
   input_required  │            │
            │      │            │
            └──────┴──┐         │
                     ▼          │
        ┌─────────────────┐     │
        │ completed │      │     │
        │ failed    │ ─── terminal
        │ cancelled │      │
        └─────────────────┘

Status values

workingInitial state. Receiver is processing.
input_requiredReceiver needs more input before it can continue.
completedTerminal — success. Result is retrievable.
failedTerminal — underlying request failed.
cancelledTerminal — cancelled by requestor.

Message Flow — tools/call That Returns a Task

1

An ordinary tools/call

Nothing special in the request. The only thing that makes a task possible is io.modelcontextprotocol/tasks in the envelope's client capabilities.

2

Immediate resultType: "task"

The task handle is the result — not a task object nested inside one. Flat fields: taskId, status, statusMessage, createdAt, lastUpdatedAt, ttlMs, pollIntervalMs. The tool has not run yet.

3

Background execution

Server spawns a thread (or hands off to a queue). The router keeps processing other requests while the task runs.

4

Polling — tasks/get

Client polls at the server's suggested pollIntervalMs. Each call returns the current snapshot without blocking. This is now the only way to retrieve a task.

5

The terminal poll carries the result

Once status is completed, the same tasks/get snapshot also carries a nested result — exactly what the original tools/call would have returned. There is no second fetch.

6

Optional notification

Receivers MAY push notifications/tasks on transition, with the full snapshot as params. Requestors MUST NOT depend on it — polling stays the contract.

Two resultTypes in one message at the end, and they mean different things: the outer one describes the poll (which completed fine), the inner one describes the work. A failed task still has a successful poll.

The Methods

MethodStatusPurpose
tasks/get—Non-blocking status poll; carries result once terminal
tasks/updatenewDeliver inputResponses to a task sitting in input_required
tasks/cancel—Best-effort cancel; -32602 if already terminal
notifications/tasksrenamedOptional status push; params are the full snapshot
tasks/resultremovedFolded into tasks/get — -32601
tasks/listremovedNothing left to scope a listing to — -32601
tools/call + params.taskremovedServers ignore the field

Why tasks/list had to go

It enumerated "your" tasks — and with sessions gone, there is no your. A listing would have to be scoped to the connection, and connections no longer mean anything, so the only honest implementation would return every caller's task ids.

Which leads directly to the security note: task ids must be unguessable. A UUID, not a counter. With no session to authenticate against, possession of the id is effectively the authorization to read the result.

Why notifications/tasks/status was renamed

The notifications/tasks/ prefix is reserved for future per-task notification channels. Squatting on it with a status message would have blocked that space, so the status push moved up to the bare notifications/tasks.

Small change, easy to miss, and it fails silently: a client listening for the old name simply never hears anything and falls back to polling.

When a Task Needs Input

A task can hit the same wall a synchronous call does: it needs roots, or a form filled in, and it cannot send a request to ask. The resolution is the same MRTR idea, spread over the polling loop.

  1. The task transitions to input_required, and the next tasks/get snapshot carries the inputRequests map.
  2. The client resolves them exactly as it would inline, then calls tasks/update with the taskId and an inputResponses map.
  3. The task returns to working and the poll loop resumes.

This is the whole reason tasks/update exists. Note what it does not need: no requestState, because a task is durable server-side state — the taskId is the continuation. The old _meta["io.modelcontextprotocol/related-task"] correlation key is gone with the server-initiated requests that needed it.

A handle and a question are alternatives, not a sequence. resultType holds one value, so the response to a tools/call is either a task handle or an input_required — never one and then the other. That forces an ordering on your handler: commit to the answer shape before the tool starts working out what it is missing. Answer input_required to a client that declared the tasks extension and the Inspector rejects it outright with "Unsupported result type input_required for tools/call: multi-round-trip auto-fulfilment is not enabled on this instance" — its task path never turns that on. Which is why the question moves to where a task can ask it: input_required as a status, resolved through tasks/update, as above.

When Not to Return a Task

Tasks add round trips. For short operations they cost more than they save — and since the decision is now yours as the server author, so is the judgement call. Answer synchronously when:

  • The call returns in under a second — the polling overhead dwarfs the work
  • The caller is plainly inside a tight loop — you are multiplying its round trips by three
  • The output is ordered and streaming — tasks are point-in-time snapshots, not a stream
  • The client did not declare the extension — not a judgement call, a rule. Run it synchronously or fail; do not hand out a handle nobody can redeem.

You might reasonably want to decide after you know the shape of the work rather than from the method name — a search over one small package hardly warrants a handle. The catch is the ordering above: by the time this server knows how big the search is, it has already had to commit to a result type. Deciding late means resolving the directory some other way first, which is exactly the trade this workshop's tool makes.

Chapter 7 Live: Call Now, Poll Later

Switch to the IDE with lessons/07-instructions.md open as the script.

  1. Tour the task records in src/main/java/com/workshop/mcp/spec/ — Task, TaskStatus (with isTerminal()), TaskResult, TasksGetParams, TasksUpdateParams. Point out TaskResult's three shapes — handle, poll snapshot, notification payload — all one record, differing only in which resultType it wears.
  2. Open tasks/TaskStore.java — the in-memory lifecycle store: create as working, transition to completed/failed/cancelled, enforce terminal-state rules, expire by TTL. Note the ids are UUIDs, and say why: with tasks/list gone, holding the id is the whole access control story.
  3. In IORouter.java, show envelope.supportsTasks() gating task creation, and the TASK_HANDLES_ENABLED flag. Then search the file for params.task and find nothing — the client's opt-in no longer exists.
  4. Walk the task branch of TOOLS_CALL — the server decides, creates the task, returns the handle, and runs key_word_search on a background thread (it sleeps ~4 seconds on purpose so the working → completed transition is observable).
  5. In Inspector: call key_word_search and get back resultType: "task" in milliseconds. Read the flat fields off the result — no nested task object to open.
  6. Poll it: tasks/get with the taskId, three or four times, until completed. Show that the terminal snapshot carries the search hits under result — and then try tasks/result and get -32601, which is the fastest way to make the removal memorable.
  7. Watch the ordering trap: in the log, the notifications/tasks for working is emitted before the tools/call reply that hands out the taskId. A client that assumed notifications only arrive after the handle would drop it. Correlation is by id, never by arrival order.
  8. Finish with cancel: start another call and tasks/cancel it mid-flight — terminal cancelled, and a second cancel is rejected with -32602.

What the audience should observe: the client asked for a keyword search and got back a receipt, without having requested one. Async is no longer something the caller opts into — it is something the server may decide, and the caller's only say is whether it can cope.
