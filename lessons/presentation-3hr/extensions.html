What Are MCP Extensions?

MCP Extensions are optional additions to the core specification. They allow the protocol to evolve without breaking backwards compatibility. An extension is only active when both sides explicitly declare support for it.

Extensions got their own slot. On revision 2026-07-28 the seven-slot capability object has a dedicated extensions map — a Map<String, Object> keyed by extension identifier. experimental still exists beside it, but it now means what its name says: genuinely non-standard, pre-specification work. Anything with a published shape belongs in extensions.

This is not cosmetic. Tasks used to be a top-level capability slot of its own; on this revision that slot is gone and tasks are declared as io.modelcontextprotocol/tasks under extensions. The rule the spec settled on is that the core capability object is closed at seven members, and everything else — however official — earns its place by identifier.

// from the server/discover result — no protocolVersion here,
// the server lists what it speaks and the client picks
{
  "resultType": "complete",
  "supportedVersions": ["2026-07-28"],
  "capabilities": {
    "completions": {},
    "prompts":   { "listChanged": false },
    "resources": { "listChanged": false, "subscribe": false },
    "tools":     { "listChanged": false },
    "extensions": {
      "io.modelcontextprotocol/ui": {
        "mimeTypes": ["text/html;profile=mcp-app"]
      },
      "io.modelcontextprotocol/tasks": {}
    }
  }
}

The client side is symmetric but arrives differently: a client declares its extensions inside _meta["io.modelcontextprotocol/clientCapabilities"].extensions on every request, because there is no handshake in which to say it once.

Extension Identifier Format

Every extension uses a namespaced identifier to avoid naming collisions:

{vendor-prefix}/{extension-name}

Official MCP Extensions

Maintained by the MCP organization under the io.modelcontextprotocol namespace:

  • io.modelcontextprotocol/tasks — long-running work
  • io.modelcontextprotocol/ui — MCP Apps
  • io.modelcontextprotocol/oauth-client-credentials
  • io.modelcontextprotocol/enterprise-managed-authorization

Note that elicitation is not on this list any more. It is a core client capability now, declared in the envelope — see the MRTR section below.

Your Own Extensions

Use your organization's reverse-domain prefix:

  • com.mycompany/analytics-dashboard
  • com.mycompany/audit-trail
  • io.github.username/custom-ext

Any MCP client that doesn't recognize your extension key simply ignores it. Neither side breaks.

The Two Official Extension Repositories

🔐 ext-auth — Authorization

Covers authorization scenarios the core protocol doesn't address:

  • OAuth 2.0 Client Credentials — machine-to-machine auth for servers calling protected APIs on their own behalf
  • Enterprise-Managed Authorization — centralized access control via corporate identity providers (Okta, Azure AD, etc.)

🖥️ ext-apps — Interactive UI

Allows MCP servers to render interactive HTML UI elements inside the conversation:

  • Charts and data visualizations
  • Forms for structured input collection
  • Video and media players
  • Custom interactive components

This is what powers MCP Apps — covered on the next page.

The Problem: A Server Can No Longer Ask

For three revisions, roots/list, sampling/createMessage, and elicitation/create worked the obvious way: the server sent a JSON-RPC request to the client, with an id, and waited for a response. That is how the previous version of this very workshop taught them.

On 2026-07-28 that no longer works. A modern client silently discards any inbound request. Not an error, not a rejection — silence. A server that tries it waits forever, and so does the user.

This is a direct consequence of statelessness, and it is worth spelling out because it is the single most disorienting change in the revision. A server→client request only makes sense if there is a durable, addressable connection to send it on. Once you can be load-balanced across instances, "the client" is not a thing the server holds a handle to; it is whoever happens to be on the other end of the request currently being processed. The only channel that reliably exists is the reply to the request you are already answering.

So the question moves into the answer.

Multi Round-Trip Requests (MRTR)

Instead of sending a request, the server returns resultType: "input_required", listing what it needs. The client gathers the answers and re-sends the original request from the top — brand new id — carrying an inputResponses map and the requestState it was handed.

1

Client declares what it can answer

In _meta["io.modelcontextprotocol/clientCapabilities"] — on this request, not once at startup. elicitation (with form and/or url) is the one this server reads and acts on, alongside the extensions map. A server must not embed a request the caller did not say it could handle. Clients also declare roots and sampling, and are right to: both are deprecated rather than removed, and SEP-2577 says clients SHOULD keep declaring them for the whole deprecation period. This server models neither, so both keys arrive and are ignored — which costs nothing, because an unrecognised key always was.

2

Server answers with a question

resultType: "input_required", an inputRequests map, and an opaque requestState. This is a perfectly ordinary JSON-RPC result to the id the client sent. The server has now finished with this request entirely and remembers nothing.

3

Client resolves each embedded request

By whatever means suits it. elicitation/create — the only one this server builds — it renders as a form and waits for the human. (A roots/list from some other server it would answer from configuration, without troubling anyone.) The answers end up as entries in a map keyed by the same keys the server used.

4

Client re-sends the original request — with a new id

Same method, same arguments, plus inputResponses and the requestState echoed back byte-exact. The new id matters: this is a new request, not a continuation of the old one. Any instance can serve it.

5

Server resumes from the state and answers

resultType: "complete" — or another input_required, if it needs a second thing. The loop can run as many times as the exchange requires.

requestState — Continuation That Travels

A server pausing mid-operation used to keep its half-finished work in memory. With sessions gone there is no memory to keep it in, so the continuation is handed to the client and comes back with the retry. It is declared as an opaque string: clients must never parse it, and servers may put whatever they like in it.

This workshop base64-encodes a tiny JSON object, which makes it readable in a demo:

"requestState": "eyJrZXl3b3JkIjoicmVjb3JkIiwic3RhZ2UiOiJkaXJlY3RvcnkifQ"

// url-safe base64, no padding — decode it and you get:
{"keyword":"record","stage":"directory"}

Two things follow that are easy to miss. Because the state leaves your process, anything sensitive in it is now on the client's disk — sign or encrypt it if it matters. And because the client can hand it back at any time, from anywhere, a server should treat it as untrusted input rather than as its own memory.

The Real Exchange — Four Messages

Captured against this server. Watch the ids.

--> {"jsonrpc":"2.0","id":1,"method":"tools/call","params":{
      "name":"key_word_search","arguments":{"keyword":"record"},
      "_meta":{ … envelope … }}}

<-- {"jsonrpc":"2.0","id":1,"result":{
      "resultType":"input_required",
      "inputRequests":{"search_directory":{
        "method":"elicitation/create","params":{ … the form … }}},
      "requestState":"eyJrZXl3b3JkIjoicmVjb3JkIiwic3RhZ2UiOiJkaXJlY3RvcnkifQ"}}

--> {"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
      "name":"key_word_search","arguments":{"keyword":"record"},
      "inputResponses":{"search_directory":{
        "action":"accept","content":{"directory":"/…/mcp/tools"}}},
      "requestState":"eyJrZXl3b3JkIjoicmVjb3JkIiwic3RhZ2UiOiJkaXJlY3RvcnkifQ",
      "_meta":{ … envelope … }}}

<-- {"jsonrpc":"2.0","id":2,"result":{
      "resultType":"complete",
      "content":[{"text":"/…/SearchContinuation.java, keyword_count=1",
                  "type":"text"}],
      "isError":false}}

inputRequests is a keyed map, not an array

The keys ("search_directory" here) are the server's own choice, and the client must return its answers under exactly those keys. A map rather than a list because several questions can be asked at once and the answers have to be matched up unambiguously — position would be a fragile way to do that.

An embedded request is not a request

{"method": "elicitation/create", "params": {…}} — the params are optional in general, though this method needs them. No jsonrpc, no id. It is a description of a question, not a message. Nothing on the wire is addressed to the client, which is exactly the point.

Only three methods may be embedded: roots/list, sampling/createMessage, and elicitation/create. All three are also absent from the inbound registry — sending one to the server is -32601, because they are things a server asks for and never things it answers. They exist in exactly one place now: inside an input_required result. This server builds exactly one of them, elicitation/create; the other two are deprecated, so there is no factory for either and nothing in the code that could emit one.
Removed and deprecated are not the same thing. This revision does both, and they land differently in the code. Removed is physical absence answering -32601 — the handshake, ping, logging/setLevel, resources/subscribe, tasks/list, notifications/roots/list_changed (SEP-2575). Deprecated is an annotation only: Roots, Sampling, and Logging are deprecated under the feature lifecycle policy (SEP-2577), yet they keep working in this revision and every revision published within a year of it, and removing them would take a separate proposal. New servers should not adopt them — pass directories as tool parameters instead of Roots, call a provider API instead of Sampling, write to stderr or OpenTelemetry instead of Logging.

Which is exactly why key_word_search has a directory argument: it is the recommended replacement for Roots, and this server has taken that migration — the roots stage it used to run is gone from the code. But watch what deprecation does not do. Roots stays in the specification, fully functional, for at least the twelve months after 2026-07-28; clients SHOULD keep declaring the capability throughout; and so the Inspector you are about to demo against still sends "roots":{"listChanged":true} in every envelope. That is correct client behaviour, and this server ignores the key. Contrast notifications/roots/list_changed, which is removed under SEP-2575 and answers -32601 — same feature, two different lifecycle mechanisms, landing in two completely different places.

Three Ways key_word_search Gets a Directory

The workshop tool needs a directory, and it holds none of its own — the router resolves them afresh for every call. There are three places one can come from, tried in this order:

  1. The directory argument on the call. This settles the question outright: none of what follows happens and the call completes in a single hop. It is also the migration the specification names in place of Roots, which is why it is first.
  2. An embedded elicitation/create. Nothing was passed, so the server asks — and asking a human is now the only question this tool has left. It used to embed a roots/list ahead of this, since a client answers that from configuration without interrupting anyone; that stage went when the code took the migration above.
  3. The server's own working directory. If the form is declined, or the client never declared elicitation to be shown one, the asking has run out — and a result the caller can reject beats an error it cannot act on.
Why keep the one-hop path at all? MRTR is optional for clients, and not every one implements it — the Inspector's own task-augmented tools/call path rejects input_required outright with "multi-round-trip auto-fulfilment is not enabled on this instance". A tool whose only route to an answer is a round trip is a tool those callers cannot use at all. Take the input as an optional argument; treat asking as the fallback.

The stage the exchange has reached is precisely what requestState is carrying: {"keyword":"record","stage":"directory"} says the form has gone out and its answer is what the retry should be read for. With one question left there is only one stage to record, but the field stays — it is what tells a retry apart from a first attempt.

The Embedded Elicitation, in Full

<-- {"jsonrpc":"2.0","id":1,"result":{
      "resultType":"input_required",
      "inputRequests":{"search_directory":{
        "method":"elicitation/create",
        "params":{
          "mode":"form",
          "message":"Pick a directory for the keyword-search tool to search in:",
          "requestedSchema":{
            "type":"object",
            "required":["directory"],
            "properties":{"directory":{
              "title":"Search Directory","type":"string",
              "description":"Absolute path to the directory the keyword search should look in"}}}}}},
      "requestState":"eyJrZXl3b3JkIjoicmVjb3JkIiwic3RhZ2UiOiJkaXJlY3RvcnkifQ"}}

elicitation/create picked up a mode field on this revision — "form" to render a schema, "url" to hand off to a browser — and lost elicitationId. It lost it because it no longer needs one: the retry is the completion signal, so there is nothing to correlate. For the same reason notifications/elicitation/complete is gone.

When the User Says No

A declined form comes back as {"action":"decline"} in the inputResponses entry. At that point the server has asked everything it can ask, so rather than fail it searches its own working directory — the same place a shell command with no path argument would look:

{"resultType":"complete",
 "content":[{"type":"text","text":"/Users/.../mcp/tools/SearchContinuation.java, keyword_count=1"}],
 "isError":false}

That fallback is this server's choice, not a protocol rule. A server that has no sensible default should end the exchange with a tool-level error instead:

{"resultType":"complete",
 "content":[{"type":"text","text":"No search directory was provided."}],
 "isError":true}

Note isError: true inside a successful result, not a JSON-RPC error object. The protocol worked perfectly; the tool could not do its job. Keeping those two distinct is what lets a model read the failure and try something else, rather than the transport treating it as a fault.

Chapter 5 Live: The MRTR Loop

Switch to the IDE with lessons/05-instructions.md open as the script.

  1. Open ServerCapabilities.java in src/main/java/com/workshop/mcp/spec/ — count the slots out loud: seven, and extensions is one of them. Then DiscoverResultBuilder.withExtension(...), and note there is no tasks slot to put tasks in any more.
  2. In IORouter.java, show RequestEnvelope.supportsElicitationForm() being consulted per request off the envelope. There is no hasElicitation field on the router — there is nowhere for one to live. Point out that this is the only top-level client capability the router asks about — the extensions map aside, which is where supportsTasks() looks — and then show a captured envelope still carrying roots: the client declares it because roots is deprecated rather than removed, and the server reads straight past it.
  3. Walk handleKeywordSearch() — the whole MRTR loop in one method, and read it in resolution order. A directory argument settles it and the tool runs at once. Otherwise, no inputResponses yet, so return InputRequiredResult.of(...) embedding elicitation/create under the key search_directory, carrying a fresh SearchContinuation. On the retry: decode the state, read the answer out of the map, search. Declined, or no elicitation declared: fall through to the working directory.
  4. Open tools/SearchContinuation.java — a two-field record, encode(), decode(). Base64 it in the terminal live (echo … | base64 -d) so the class sees there is no magic in it, then make the point that a client is not allowed to do what you just did.
  5. Run inspector/modern-mrtr.sh before touching the GUI — four messages, printed plainly, easy to read together. Have the class find the two different ids and the identical requestState.
  6. In Inspector: call key_word_search with keyword record and a directory. One request, one complete result — the baseline, and the shape a caller that cannot do round trips is left with.
  7. Now drop the directory argument and call it again. This time the Search Directory form appears. Submit an absolute path, and show the second request going out with inputResponses and the stage: "directory" state — same logical call, two JSON-RPC exchanges.
  8. Decline the form once — the search still returns, now rooted at the server's working directory. Then point at the isError: true shape above and draw the distinction between a tool that failed and a protocol that failed.

What the audience should observe: the server never sent a single message that was not a reply. Every question it asked, it asked inside an answer — and that constraint, not a style preference, is what MRTR exists to work around. The same pattern reappears in the Tasks chapter, where tasks/update delivers inputResponses to a task that is waiting.
