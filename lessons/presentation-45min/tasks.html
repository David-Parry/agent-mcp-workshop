Chapter 7 Extension — io.modelcontextprotocol/tasks

The Problem Tasks Solve

The synchronous tools/call shape works fine for fast operations — sub-second searches, lookups, small computations. It falls apart for anything that takes longer than a polite roundtrip: large-scale processing, batch jobs, ML inference, external API calls with retries.

Tasks split a request into two trips: the receiver immediately answers resultType: "task" with a taskId and a status of working, runs the work in the background, and lets the requestor poll or cancel on its own schedule.

In 2026-07-28 tasks are no longer a top-level capability. They moved into an extension, declared under capabilities.extensions — which also means a server can only hand back a task to a client that declared that extension on the very request being answered.

What Changes vs. Plain tools/call

ConcernWithout TasksWith Tasks
Long operationsHold the connection openAnswer fast, poll later
Crash recoveryResult lost when stream dropsRetrievable until ttlMs expires
Concurrent workOne slow call blocks the LLMLLM dispatches and continues
Sessionless transportNothing to hold the work openThe taskId is the continuation

Capability Negotiation

Both sides declare the extension by identifier. Empty {} markers are intentional — presence is the signal.

Server declares (in its server/discover result)

{
  "capabilities": {
    "extensions": {
      "io.modelcontextprotocol/tasks": {}
    }
  }
}

The old top-level tasks slot — with its list, cancel, and requests sub-maps — no longer exists.

Client declares (in params._meta of every request)

"io.modelcontextprotocol/clientCapabilities": {
  "extensions": {
    "io.modelcontextprotocol/tasks": {}
  }
}

Per request, not once per session. A client that omits it on one call must not be handed a task on that call.

Who Decides — and It Is Not the Client

Task creation is now the server's decision. The params.task opt-in a client used to send was removed, and servers MUST ignore one if it arrives:

// what a client used to send, and what a server must now ignore
"params": { "task": { "ttl": 60000 } }   // ← no longer part of the protocol

The tool-level execution.taskSupport field is gone too — it was removed from tools/list entirely, and clients strip it silently if a server still emits it. So there is nothing left to negotiate per tool: the server looks at the request, decides, and answers with either a result or a handle.

The one hard rule: never return a task to a client that did not declare the extension on that request. A client that cannot poll must not be handed something to poll — it would simply wait forever.

The Task Lifecycle

Tasks are state machines with three terminal states. Receivers are forbidden from moving a terminal task back into working.

                [*]
                 │
                 ▼
        ┌────────────────┐
        │    working     │◄─────┐
        └────────────────┘      │
            │      │            │
            ▼      ▼            │
   input_required  │            │
            │      │            │
            └──────┴──┐         │
                     ▼          │
        ┌─────────────────┐     │
        │ completed │      │     │
        │ failed    │ ─── terminal
        │ cancelled │      │
        └─────────────────┘

Status values

workingInitial state. Receiver is processing.
input_requiredReceiver needs more input before it can continue.
completedTerminal — success. Result is retrievable.
failedTerminal — underlying request failed.
cancelledTerminal — cancelled by requestor.

Message Flow — tools/call That Answers With a Handle

1

An ordinary request

Client sends a plain tools/call. Nothing marks it as special — it just happens to declare io.modelcontextprotocol/tasks in its _meta envelope.

2

Immediate handle — resultType: "task"

Server replies in milliseconds with the flat task shape: { resultType: "task", taskId, status: "working", statusMessage, createdAt, lastUpdatedAt, ttlMs, pollIntervalMs }. The underlying tool has not run yet.

3

Background execution

Server spawns a thread (or hands off to a queue). The router keeps processing other requests while the task runs.

4

Polling — tasks/get

Client polls at the server's suggested pollIntervalMs, using ids like inspector-ext-1, inspector-ext-2… Each call returns the current snapshot with resultType: "complete", without blocking.

5

Retrieval — the same tasks/get

Once the status reaches completed, that snapshot also carries the underlying result — exactly what the original tools/call would have returned. There is no second method to call: tasks/result was removed.

6

Optional notification

Receivers MAY push notifications/tasks on transition, with the full task snapshot as its params. Requestors MUST NOT depend on it — polling stays the contract.

When a Task Needs Something — tasks/update

A task can hit the same wall a synchronous call does: it needs a form answer before it can finish. It parks in input_required, and the poll that finds it there comes back carrying the question:

// tasks/get, while the task waits
{
  "resultType": "complete",
  "taskId": "3dab39bc-…",
  "status": "input_required",
  "inputRequests": {
    "search_directory": { "method": "elicitation/create", "params": { … } }
  }
}

The client resolves it and hands the answers back — and this is the only thing tasks/update exists to do:

// tasks/update, delivering the answer
{
  "method": "tasks/update",
  "params": {
    "_meta": { "…the envelope…" },
    "taskId": "3dab39bc-…",
    "inputResponses": {
      "search_directory": { "action": "accept", "content": { "directory": "/…" } }
    }
  }
}

Same MRTR vocabulary as Chapter 5 — inputRequests, inputResponses, keyed by the server's own labels. The difference is the carrier: a synchronous call is retried under a new id, whereas a task already has an identity, so the taskId does the correlating and no requestState is needed.

Note what is not here: the old _meta.io.modelcontextprotocol/related-task wrapper. Task messages are a flat shape now, and taskId is the correlation.

A handle and a question are alternatives, not a sequence. resultType holds one value, so the response to a tools/call is either a task handle or an input_required — never one then the other. The server has to commit to the shape before the tool starts working out what it is missing. Get that order wrong and a task-declaring client gets "Unsupported result type input_required for tools/call" back from the Inspector, whose task path never enables auto-fulfilment. So key_word_search hands a task client its handle immediately — and then asks the same question at the task level, as an input_required status answered by tasks/update. Nothing is given up by committing early; the question simply moves off the call and onto the task.

When Not to Hand Back a Task

Tasks add round trips. For short operations they cost more than they save — and since the choice is now yours as the server author, it is your judgement call on every request. Answer inline when:

  • The call returns in under a second — the polling overhead dwarfs the work
  • The client did not declare the extension — not a judgement call, a hard rule
  • You need ordered streaming output — tasks are point-in-time, not a stream. Reach for subscriptions/listen instead
  • The result is small and cacheable — ttlMs on a plain result may buy more than a task would

In this workshop the switch is the TASK_HANDLES_ENABLED constant in IORouter — flipped deliberately so the same call can be demoed in both shapes.
