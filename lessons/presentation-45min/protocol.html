Transport Layer — The STDIO Foundation

MCP communicates over standard I/O streams by default. The host process starts your server as a subprocess and communicates through stdin/stdout. Every message is a single JSON line.

Critical Rule: Never write anything to System.out except JSON-RPC messages. All debugging and logging must go to a file. Writing non-JSON to stdout breaks the protocol connection immediately.

IOHandler — The Communication Hub

The IOHandlerImpl class manages all I/O with three responsibilities:

📥 Input Reading

public void startInputReader() {
    Scanner scanner = new Scanner(System.in);
    running.set(true);
    while (running.get()) {
        if (!scanner.hasNextLine()) {
            running.set(false); break;
        }
        String line = scanner.nextLine();
        logger.log("[API][RECEIVED]" + line);
        publishLine(line); // → listeners
    }
}

Runs on a dedicated thread. Publishes each JSON line to all registered listeners via the Observer pattern.

📤 Output Emission

public void emit(Object message) {
    String text = gson.toJson(message);
    logger.log("[API][SENT]: " + text);
    writer.println(text);
    writer.flush(); // immediate
}

Serializes any Java object to JSON via Gson. Immediately flushes — MCP clients expect real-time responses.

Key Design Choices

  • CopyOnWriteArrayList for thread-safe listener management
  • AtomicBoolean for safe running-state across threads
  • Process-specific log files using PID — no conflicts when multiple servers run
  • Router interface — the IOHandler doesn't know what messages mean, it just moves them

JSON-RPC 2.0 — The Message Protocol

MCP uses JSON-RPC 2.0 as its wire format. Every message is a JSON object with a defined structure. There are four message types:

Request

Client → Server

{
  "jsonrpc": "2.0",
  "id": 6,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion":
        "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities":
        { "roots": { "listChanged": true } }
    }
  }
}

Has an id — expects a Response back with the same id, in the same JSON type. Carries the _meta envelope, on every single request.

Response

Server → Client

{
  "jsonrpc": "2.0",
  "id": 6,
  "result": {
    "resultType": "complete",
    "tools": [{
      "name": "key_word_search",
      "description": "..."
    }],
    "ttlMs": 60000,
    "cacheScope": "public"
  }
}

Returns result with the same id. resultType is mandatory on every result; ttlMs and cacheScope only on the five cacheable methods.

Notification

Either Side → Other Side

{
  "jsonrpc": "2.0",
  "method": "notifications/tasks",
  "params": { "taskId": "3dab39bc-…",
              "status": "working" }
}

No id — fire-and-forget. No Response expected. This is the only direction a server may still speak unprompted.

Error Response

Server → Client (on failure)

{
  "jsonrpc": "2.0",
  "id": 7,
  "error": {
    "code": -32601,
    "message": "Method not found"
  }
}

Standard codes: -32700 Parse Error, -32600 Invalid Request, -32601 Method Not Found, -32602 Invalid Params.

Request Ids Are Strings or Numbers

JSON-RPC has always allowed both, and 2026-07-28 clients use both freely: "server-discover-probe-1" for discovery, "listen:0" for a subscription, "inspector-ext-1"… while polling a task, and plain integers for everything else. A server must echo the id back in exactly the form it arrived — a string id must not come back as a number.

What that costs in Java: this repo's id field used to be a Long. The first modern client to connect sent "server-discover-probe-1" and the server died with NumberFormatException: For input string: "server-discover-probe-1". The fix is spec/RequestId.java — a small union type — plus RequestIdTypeAdapter to remember which arm arrived.

MCP Method Namespace

All MCP methods follow a category/action naming convention:

server/discover

Versions, capabilities, identity — and no session

resources/*

list, read — discover and fetch content

tools/*

list, call — discover and execute tools

prompts/*

list, get — discover and fetch templates

tasks/*

get, update, cancel — deferred work, polled

subscriptions/*

listen — one long-lived request, many notifications

roots/list, sampling/createMessage and elicitation/create are still method names, but no longer messages a server may send. They now travel inside a result — see Chapter 5. Sending any of them to this server is -32601, and two of the three, roots and sampling, are additionally deprecated under SEP‑2577, so this server embeds only elicitation/create.

Stateless by Design — Now Literally

Older revisions were stateless in spirit and stateful in practice: an initialize handshake opened a session, and everything after it assumed that session existed. 2026-07-28 removed the handshake outright. There is no first message, no session, nothing to resume. This means:

  • Any request can arrive at any time, in any order, as the very first thing the server ever sees
  • Every request carries its own context — the _meta envelope replaces what the handshake used to establish
  • Servers can be scaled horizontally, or restarted mid-conversation, and no client notices
  • Debugging is simpler — each message really is self-contained now

Capability-Based Feature Detection

The client learns what the server can do from server/discover. The server learns what the client can do from _meta["io.modelcontextprotocol/clientCapabilities"] — on every request, because there is no session to remember it in. A server may only hand back a task to a request that declared the tasks extension; it may only embed elicitation/create in a result if that same request declared elicitation. No guessing — explicit opt-in, re-stated every time.
