What Are MCP Extensions?

MCP Extensions are optional additions to the core specification. They allow the protocol to evolve without breaking backwards compatibility. An extension is only active when both sides declare support for it — the server in its server/discover result, the client in the _meta envelope of each request.

The Extensions Map: Extensions live in the extensions field of ServerCapabilities — a Map<String, Object> where each key is an extension identifier and each value is extension-specific configuration. This is one of the seven capability slots, promoted in 2026-07-28 from the looser experimental map it grew out of. experimental still exists for genuinely ad-hoc work. 
// the server, in its server/discover result
{
  "supportedVersions": ["2026-07-28"],
  "capabilities": {
    "tools": { "listChanged": false },
    "prompts": { "listChanged": false },
    "resources": { "listChanged": false, "subscribe": false },
    "extensions": {
      "io.modelcontextprotocol/tasks": {},
      "io.modelcontextprotocol/ui": {
        "mimeTypes": ["text/html;profile=mcp-app"]
      }
    }
  }
}

// the client, in params._meta of every request
"io.modelcontextprotocol/clientCapabilities": {
  "roots": { "listChanged": true },   // deprecated — ignored here
  "elicitation": { "form": {}, "url": {} },
  "extensions": { "io.modelcontextprotocol/tasks": {} }
}

Because the client re-declares on every request, capability negotiation is now a per-request fact. The same tool can answer one client inline and hand another a task handle, decided fresh each time.

Extension Identifier Format

Every extension uses a namespaced identifier to avoid naming collisions:

{vendor-prefix}/{extension-name}

Official MCP Extensions

Maintained by the MCP organization under the io.modelcontextprotocol namespace:

  • io.modelcontextprotocol/tasks — this server declares it
  • io.modelcontextprotocol/ui — this server declares it
  • io.modelcontextprotocol/oauth-client-credentials
  • io.modelcontextprotocol/enterprise-managed-authorization

Elicitation is no longer an extension — it is a core client capability, reached through MRTR.

Your Own Extensions

Use your organization's reverse-domain prefix:

  • com.mycompany/analytics-dashboard
  • com.mycompany/audit-trail
  • io.github.username/custom-ext

Any MCP client that doesn't recognize your extension key simply ignores it. Neither side breaks.

The Two Official Extension Repositories

🔐 ext-auth — Authorization

Covers authorization scenarios the core protocol doesn't address:

  • OAuth 2.0 Client Credentials — machine-to-machine auth for servers calling protected APIs on their own behalf
  • Enterprise-Managed Authorization — centralized access control via corporate identity providers (Okta, Azure AD, etc.)

🖥️ ext-apps — Interactive UI

Declared as io.modelcontextprotocol/ui. Allows MCP servers to render interactive HTML UI elements inside the conversation:

  • Charts and data visualizations
  • Forms for structured input collection
  • Video and media players
  • Custom interactive components

This is what powers MCP Apps — covered on the next page.

MRTR — Asking, When You Cannot Call

Roots, sampling, and elicitation used to be server-initiated requests: the server wrote a JSON-RPC request to the client and waited for a response. That is over. In 2026-07-28 a server MUST NOT send requests, and modern clients silently discard any that arrive — no error comes back, the message simply vanishes.

Multi Round-Trip Requests (MRTR): instead of calling the client, the server answers with resultType: "input_required" and embeds the request it wanted to make. The client gathers the answers and re-sends the original request — as a brand new request with a brand new id — carrying inputResponses and the server's requestState echoed back byte-exact.

The MRTR Flow

1

Client declares what it can answer

In the _meta envelope of the tools/call itself: "elicitation": { "form": {}, "url": {} }, plus the extensions map. No handshake to remember it, so it rides along every time. A real client also sends "roots": { "listChanged": true } and "sampling"; both are deprecated under SEP‑2577, this server models neither, and an unrecognised key costs nothing.

2

Server replies with a question, not the answer

tools/call key_word_search arrives with no directory argument, so there is nothing to search. The server replies resultType: "input_required", embedding elicitation/create under the key search_directory, plus a requestState holding the keyword and how far the exchange has got.

3

Client resolves the embedded request

It renders the form described by params.requestedSchema and waits for the human to type a path. There used to be a cheaper question ahead of this one — an embedded roots/list, answered from client configuration without troubling anyone — but roots is deprecated, and the directory argument replaced it.

4

Client re-sends the original request under a new id

Not a response to anything — a fresh tools/call, id 1 → 2, with inputResponses.search_directory filled in and requestState returned unchanged.

5

Server decodes its own state and continues

SearchContinuation.decode(requestState) recovers the keyword and stage, the form answer supplies the directory, and the search finally runs. The server remembered nothing between the two requests — it did not have to.

6

And when the asking runs out

A declined form, or a client that cannot show one at all, leaves the server with no answer and nothing left to ask. It searches its own working directory rather than failing — the call always produces a result.

Always leave a one-hop path. MRTR is optional for clients, and not every one implements it — the Inspector's own task-augmented tools/call path rejects input_required outright. So key_word_search also takes directory as an optional argument: supply it and the call completes in a single hop, omit it and the round trips above kick in. A tool whose only route to an answer is a round trip is a tool those clients cannot use at all.

The Embedded Request (Server → Client, inside a result)

Note what is missing from the embedded request: no jsonrpc, no id. It is identified purely by its method and correlated by the key it sits under.

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "search_directory": {
        "method": "elicitation/create",
        "params": { "mode": "form" }
      }
    },
    "requestState": "eyJrZXl3b3JkIjoicmVjb3JkIiwic3RhZ2UiOiJkaXJlY3RvcnkifQ"
  }
}

inputRequests is a keyed map, not an array — search_directory is the server's own label, and the answer comes back under exactly that key. Only three methods may ever be embedded: roots/list, sampling/createMessage, and elicitation/create — and this server builds only the last of them, the other two being deprecated under SEP‑2577. params is abbreviated above; here it is in full.

The Form Itself

The whole params object, exactly as the client receives it and renders it:

"inputRequests": {
  "search_directory": {
    "method": "elicitation/create",
    "params": {
      "mode": "form",
      "message": "Pick a directory for the keyword-search tool to search in:",
      "requestedSchema": {
        "type": "object",
        "required": ["directory"],
        "properties": {
          "directory": {
            "title": "Search Directory",
            "type": "string",
            "description": "Absolute path to the directory the keyword search should look in"
          }
        }
      }
    }
  }
}

mode is new: "form" for an in-conversation form, "url" for an out-of-band page. The old elicitationId field is gone — under MRTR the client reports the outcome by retrying the original request, so there is nothing left to correlate.

The Retry (Client → Server)

{
  "jsonrpc": "2.0",
  "id": 2,                        // ← NEW id, not a response to id 1
  "method": "tools/call",
  "params": {
    "_meta": { "…the envelope, again…" },
    "name": "key_word_search",
    "arguments": { "keyword": "record" },
    "inputResponses": {
      "search_directory": {       // ← keyed by the server's own label
        "action": "accept",
        "content": { "directory": "/…/mcp/tools" }
      }
    },
    "requestState": "eyJrZXl3b3JkIjoicmVjb3JkIiwic3RhZ2UiOiJkaXJlY3RvcnkifQ"
  }
}

An input response is the bare result the embedded method would have returned — {"action": "accept", "content": {...}}, not anything JSON-RPC-shaped. Only accept carries content; the user may equally answer "decline" or "cancel", and then the server falls back to its working directory.

Why requestState exists: it is an opaque string, not JSON. Sessions are gone, so the server has nowhere to keep what it learned while producing the interim result — the continuation state has to travel to the client and back. This repo base64-encodes {"keyword":"record","stage":"directory"} into it, but the protocol guarantees only that the client returns the exact bytes. Treat it as a cookie you wrote to yourself.

Inspector: See the MRTR Loop Live

Two ways in — the Inspector UI, or inspector/modern-mrtr.sh, which walks both paths in one go.

  • Connect — nothing is asked. No request of any kind goes out from the server at startup, because a server has no way to send one
  • Open Tools and invoke key_word_search with a keyword and a directory — one request, one complete result. That is the baseline to contrast against
  • Now drop the directory argument and invoke it again
  • The answer is resultType: "input_required" with inputRequests.search_directory — a result, not a request. Point at the missing id inside it
  • The Search Directory form appears, carrying mode: "form". Submit an absolute path and the client re-sends tools/call under a new id. Compare the two ids in the trace
  • Base64-decode the requestState on screen: {"keyword":"record","stage":"directory"} — the server's memory, in the client's hands
  • Point at the client's own "roots": {"listChanged": true} in the envelope while you are there: the Inspector still declares it, correctly, because roots is deprecated rather than removed. The server never reads it
  • Decline that form — the search still returns, rooted at the server's working directory. There is no dead end to demo, by design
