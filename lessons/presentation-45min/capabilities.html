Discovery & Routing

There is no handshake. Revision 2026-07-28 deleted initialize, and with it the whole idea of a session. A client learns what a server can do by asking server/discover, and then re-states the terms of the conversation on every single request.

server/discover (Client → Server)

{
  "jsonrpc": "2.0",
  "id": "server-discover-probe-1",
  "method": "server/discover",
  "params": { "_meta": {
    "io.modelcontextprotocol/protocolVersion":
      "2026-07-28",
    "io.modelcontextprotocol/clientInfo": {
      "name": "inspector-cli",
      "version": "2.5.0"
    },
    "io.modelcontextprotocol/clientCapabilities": {
      "roots": { "listChanged": true },
      "extensions": {
        "io.modelcontextprotocol/tasks": {}
      }
    }
  }}
}

Note the string id. Ids may be strings or numbers now, and a server must echo one back in exactly the form it arrived.

server/discover result (Server → Client)

{
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "completions": {},
      "prompts": { "listChanged": false },
      "resources": {
        "listChanged": false,
        "subscribe": false
      },
      "tools": { "listChanged": false },
      "extensions": { "...": "..." }
    },
    "instructions": "Searches a project…",
    "ttlMs": 60000,
    "cacheScope": "public",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "agent-mcp-workshop",
        "version": "0.0.1"
      }
    }
  }
}

No single protocolVersion: the server lists what it speaks and the client picks. And serverInfo moved out of the body into _meta.

The Request Envelope — What Replaced the Handshake

Every request carries these keys in params._meta. Get them wrong and the request is refused before any handler sees it:

KeyRequired?If missing or wrong
io.modelcontextprotocol/protocolVersionRequired-32602, or -32022 with data.supported if the revision is unknown
io.modelcontextprotocol/clientCapabilitiesRequired-32602; -32021 when a needed capability is absent
io.modelcontextprotocol/clientInfoRecommendedNothing — the server just does not know who is calling
io.modelcontextprotocol/logLevelOptionalAbsent means the server MUST NOT emit notifications/message

Server Capabilities — Exactly Seven Slots

The capability object is now fixed at seven optional members. Everything beyond the core protocol — tasks included — is declared under extensions, keyed by identifier:

"capabilities": {
  "experimental": { … },   // non-standard, ad hoc
  "logging":      { … },   // can emit notifications/message
  "completions":  { … },   // answers completion/complete
  "prompts":      { "listChanged": false },
  "resources":    { "listChanged": false, "subscribe": false },
  "tools":        { "listChanged": false },
  "extensions": {          // ← the old top-level "tasks" slot is gone
    "io.modelcontextprotocol/tasks": {},
    "io.modelcontextprotocol/ui": {
      "mimeTypes": ["text/html;profile=mcp-app"]
    }
  }
}

resources.subscribe survives even though resources/subscribe was removed — it now gates the resourceSubscriptions field of subscriptions/listen.

Message Routing — The IORouter Switch

After deserialization, every message is routed through a switch expression based on its method name. Note what the registry no longer contains:

case SERVER_DISCOVER    → discoverResult()          // answered before any version check
// ── everything below first passes envelopeFor(request) ──
case RESOURCES_LIST     → handleResourcesList(request)
case RESOURCES_TEMPLATES_LIST → empty list, but it must be answered
case RESOURCES_READ     → handleResourcesRead(request)
case TOOLS_LIST         → handleToolsList(request)
case TOOLS_CALL         → handleKeywordSearch(request)  // may return input_required
case PROMPTS_LIST       → handlePromptsList(request)
case PROMPTS_GET        → handlePromptsGet(request)
case COMPLETION_COMPLETE→ handleCompletion(request)
case SUBSCRIPTIONS_LISTEN → acknowledgeSubscription(request)
case TASKS_GET | TASKS_UPDATE | TASKS_CANCEL → tasks extension
default                 → error(id, METHOD_NOT_FOUND)
Deletion is physical. initialize, notifications/initialized, ping, logging/setLevel, notifications/roots/list_changed, resources/subscribe, resources/unsubscribe, tasks/result, and tasks/list are simply absent from the registry — so they answer -32601 Method not found. Not deprecated. Gone.

STDIO Discipline

  • All logs go to inspector/logs/mcp-<pid>.log — never to System.out
  • Writing non-JSON to stdout breaks the protocol immediately
  • The client reads stdout byte-by-byte looking for newline-delimited JSON

Resources — Serving Content from the Server

Resources allow the server to expose any content the client can discover and read. Our server exposes 70+ Javadoc HTML files bundled inside the JAR.

resources/list — Discovery

Returns a paginated list of all available resources with URI, name, description, and MIME type:

{
  "resultType": "complete",
  "resources": [{
    "uri": "javadoc/com/workshop/mcp/spec/Capability.html",
    "name": "Capability",
    "description": "Represents the capability...",
    "mimeType": "text/html"
  }],
  "nextCursor": "pageNext",
  "ttlMs": 60000,
  "cacheScope": "public"
}

resources/read — Retrieval

Returns the actual content of a specific resource by URI:

{
  "resultType": "complete",
  "contents": [{
    "uri": "javadoc/...",
    "mimeType": "text/html",
    "text": "..."
  }],
  "isError": false,
  "ttlMs": 60000,
  "cacheScope": "public"
}

Two Fields on Every Result — and Two More on Five of Them

resultType is required on every result in this revision. It is one of "complete", "input_required", or "task" — the client reads it first to know whether it is holding an answer, a question, or a receipt.

Cacheable results must also carry ttlMs (non-negative) and cacheScope ("public" or "private"). There are exactly five:

Carries ttlMs + cacheScopeMust NOT carry them
tools/list
prompts/list
resources/list
resources/templates/list
resources/read		 prompts/get
tools/call
completion/complete
…and every other result

The split is easy to remember: lists and reads are cacheable, invocations are not. Caching is how a sessionless protocol claws back the round trips the handshake used to save.

JavadocResources — Classpath Loading

  • HTML Javadoc files are bundled inside the JAR via Gradle resources
  • JSoup parses the HTML to extract documentation summaries for descriptions
  • File paths become resource URIs: javadoc/com/workshop/mcp/spec/Capability.html
  • Making the server self-contained — no external files required
  • resources/templates/list must be answered whenever any resource capability is advertised — even with an empty list, as this server does

Tools — Executable Functionality

Tools are functions the LLM can call. Defined with JSON Schema for parameter validation, they are the primary integration point between the LLM and your business logic.

tools/list — Discovery

{
  "resultType": "complete",
  "tools": [{
    "name": "key_word_search",
    "description": "Searches for a keyword across all files in a project.",
    "inputSchema": {
      "type": "object",
      "properties": {
        "keyword": {
          "type": "string",
          "description": "keyword to search for"
        }
      },
      "required": ["keyword"]
    },
    "_meta": {
      "ui": { "resourceUri": "ui://keyword-search/mcp-app.html" },
      "ui/resourceUri": "ui://keyword-search/mcp-app.html"
    }
  }],
  "ttlMs": 60000,
  "cacheScope": "public"
}

No execution / taskSupport — this revision removed it, and clients strip it silently. The directory is not a tool param either: the server asks for it over MRTR (Ch 5).

tools/call — Execution

{
  "method": "tools/call",
  "params": {
    "_meta": { "…the envelope…" },
    "name": "key_word_search",
    "arguments": {
      "keyword": "record"
    }
  }
}

// Response — no ttlMs, no cacheScope
{
  "resultType": "complete",
  "content": [{
    "type": "text",
    "text": "/path/api.http, keyword_count=1"
  },
  // ... more files
  ],
  "isError": false
}

Two other shapes can come back from this same call: "input_required" when the server still needs something, and "task" when it hands back a receipt to poll.

KeyWordSearch Implementation

  • Walks the directory tree recursively from each configured root
  • Roots arrive as an embedded roots/list answer in a follow-up tools/call (Ch 5) — never as a tool parameter, and never by the server calling the client
  • Counts occurrences of keyword per file (case-insensitive)
  • Returns one text content item per matching file with its count
  • The JSON Schema required array enables client-side validation before the request is even sent
💬

Prompts — User-Friendly Templates

Prompts are reusable templates that guide users and clients in composing effective tool calls. They appear as autocomplete suggestions in MCP-compatible clients.

prompts/list — Discovery

{
  "resultType": "complete",
  "prompts": [{
    "name": "search_keyword",
    "description": "Creates a prompt to search for a word using the key_word_search tool.",
    "arguments": [{
      "name": "keyword",
      "description": "The word to search for",
      "required": true
    }]
  }],
  "nextCursor": "nextPage",
  "ttlMs": 60000,
  "cacheScope": "public"
}

prompts/get — Execution

{
  "method": "prompts/get",
  "params": {
    "_meta": { "…the envelope…" },
    "name": "search_keyword",
    "arguments": { "keyword": "record" }
  }
}

// Response — cacheable neighbour, but NOT cacheable itself
{
  "resultType": "complete",
  "messages": [{
    "role": "user",
    "content": {
      "type": "text",
      "text": "Start from the root of the project and use the key_word_search tool to search for this specific keyword: 'record'"
    }
  }]
}

How the Three Capabilities Work Together

CapabilityWhat It ExposesPrimary Use
ResourcesStatic content (Javadoc HTML)Documentation, reference data, context for the LLM
ToolsExecutable functions (keyword search)Dynamic operations, data retrieval, system interaction
PromptsGuided templatesUX layer — makes tools discoverable and easy to use

MCP Inspector: Explore All Three Capabilities

Switch to the IDE. The server should already be running from the previous demo.

  • Click "List Resources" → see 70+ Javadoc files listed, plus ttlMs and cacheScope on the result
  • Click a resource → read its HTML content via resources/read
  • Click "List Tools" → see key_word_search with its JSON Schema, and no execution block
  • Call key_word_search with keyword="record" → the first answer is resultType: "input_required", not results. That is the MRTR loop starting
  • Click "List Prompts" → see search_keyword prompt
  • Execute the prompt with a keyword — note the result carries resultType but no cache fields
  • Switch to Runtime Facts to see what discovery reported
