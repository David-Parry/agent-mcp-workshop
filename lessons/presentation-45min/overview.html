What is the Model Context Protocol?

MCP is an open standard that defines how AI applications, language models, and external services communicate. Think of it as the USB-C of AI integrations — a universal connector that lets any LLM-based application speak to any data source or tool without custom glue code.

MCP uses JSON-RPC 2.0 as its message format and runs over STDIO (and HTTP/SSE). As of revision 2026-07-28 it is stateless: there is no handshake and no session, only the client sending requests that each carry their own context — and servers answering, or asking back inside those answers.

The Four Actors

🤖

Agent

Initiates the request — an agent acting on a goal, or a human typing a question in the chat interface.

📱

Client

Claude Desktop, Claude Code, VS Code Copilot, Cursor — the client that owns the conversation and manages MCP connections.

🧠

LLM

The language model (e.g., Claude) that processes requests, reasons about them, and decides when to call tools.

🔌

MCP Server

Your code. Exposes tools, resources, and prompts that the LLM can discover and invoke. What we're building today.

Flow Explanation

1. Agent Interaction

The process begins when an Agent sends a request to the Client. This could be a question, command, or any input that requires processing.

2. LLM Processing

The Client forwards the request to the LLM, which processes the agent's input. During processing, the LLM may determine it needs external capabilities to give a complete answer.

3. Tool/Function Call

When the LLM requires external data or functionality, it makes a Tool/Function Call back to the Client. This is the MCP entry point — the LLM is requesting access to a registered tool or resource.

4. MCP Server Interaction

The Client routes this request to the appropriate MCP Server. The server processes the request, which might involve:

  • Accessing databases or file systems
  • Calling external APIs
  • Performing computations
  • Retrieving specific resources or documentation

5. Response Chain

The MCP Server returns its response to the Client, which provides this additional information back to the LLM. The LLM processes this new information and generates a comprehensive final response.

6. Final Delivery

The Client delivers the LLM's final response back to the Agent, completing the request-response cycle.

Key Protocol Features

🔌 Transport Agnostic

Works over STDIO, Server-Sent Events (SSE), and Streamable HTTP. Protocol logic is independent of transport.

➡️ Client-Initiated

Only the client sends requests. A server that needs user input embeds the question in its result and the client comes back — the Multi Round-Trip Request.

🧩 Extensible

New capabilities can be added via the extensions map — keyed by reverse-DNS identifier — without breaking existing implementations.

📋 Capability Negotiation

The client learns the server's capabilities from server/discover; the server learns the client's from the _meta envelope on every request. No guessing — opt-in features only.

🔧 Tools

Functions the LLM can call. Defined with JSON Schema so clients can validate parameters before sending.

📄 Resources

Data sources the client can discover and read. URIs + MIME types. Supports pagination with cursors.

💬 Prompts

Reusable prompt templates that guide clients in composing effective tool calls.

🤝 Sampling

Server can ask the client to run an LLM inference on its behalf — embedded in a result, then answered on the next round trip. Deprecated on 2026-07-28; the guidance is to call a provider API directly, so this server does not implement it.

Why Build an MCP Server in Java?

  • Existing codebases: Most enterprise Java code can be wrapped and exposed as MCP tools with minimal change
  • Type safety: Java's type system maps naturally to JSON Schema for tool parameters
  • JVM ecosystem: Access to the full Maven/Gradle ecosystem for any integration you need
  • One server, many clients: Claude Code, Cursor, Windsurf, VS Code Copilot — any MCP-compatible host can use your server
