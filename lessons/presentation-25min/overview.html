MCP Communication Architecture

The Model Context Protocol (MCP) enables seamless communication between applications, language models, and external services. The diagram below illustrates the complete request-response flow in an MCP-enabled system.

sequenceDiagram participant Agent participant Client participant LLM as LLM (Language Model) participant MCP as MCP Server Agent->>Client: Send Request Client->>LLM: Forward Request LLM->>LLM: Process Request LLM->>Client: Request Additional Information
(Tool/Function Call) Client->>MCP: Route Request to MCP Server MCP->>MCP: Process Request MCP->>Client: Return Response Client->>LLM: Provide Additional Information
(MCP Response) LLM->>LLM: Process with New Information LLM->>Client: Generate Final Response Client->>Agent: Deliver Response

Flow Explanation

1. Agent Interaction

The process begins when an Agent sends a request to the Client. This could be a question, command, or any input that requires processing.

2. LLM Processing

The Client forwards the request to the LLM (Language Model), which begins processing the agent's input. During this processing, the LLM may determine that it needs additional information or capabilities to provide a complete response.

3. Tool/Function Call

When the LLM requires external data or functionality, it makes a Tool/Function Call back to the Client. This is where MCP comes into play - the LLM is requesting access to external resources, data, or capabilities.

4. MCP Server Interaction

The Client routes this request to the appropriate MCP Server. The MCP Server processes the request, which might involve:

  • Accessing databases or file systems
  • Calling external APIs
  • Performing computations
  • Retrieving specific resources or data

5. Response Chain

The MCP Server returns its response to the Client, which then provides this additional information back to the LLM. The LLM processes this new information along with the original request to generate a comprehensive final response.

6. Final Delivery

The Client delivers the LLM's final response back to the Agent, completing the request-response cycle.

Key Benefits of MCP Architecture

  • Modularity: MCP servers can be developed and deployed independently
  • Extensibility: New capabilities can be added without modifying the core application
  • Security: Controlled access to external resources through well-defined protocols
  • Standardization: Consistent interface for LLM-to-external-service communication
  • Scalability: Multiple MCP servers can handle different types of requests

Protocol Features

The MCP protocol supports various types of interactions:

  • Tools: Function calls that the LLM can invoke
  • Resources: Data sources that can be read or accessed
  • Prompts: Reusable prompt templates
  • Sampling: AI model interaction capabilities — deprecated on 2026-07-28, so this server does not implement it
  • Real-time Updates: Dynamic notifications of changes

Three newer pieces build on those foundations, and this server implements all three:

  • Round trips: the server asks the user a question by answering the call, then the client re-sends it with the answer
  • MCP Apps: a tool returns an interactive UI instead of a wall of text
  • Tasks: call now, fetch later — long-running work stops blocking

One Thing to Keep in Mind: It Is Stateless

Revision 2026-07-28 removed the initialize handshake, and with it the whole notion of a session. That single change explains almost everything else you will see today.

  • Discovery replaces the handshake. server/discover reports which revisions a server speaks, what it can do, and who it is — and creates nothing.
  • Every request re-states the lifecycle. The protocol version and the client's capabilities travel in params._meta on each call, because the server cannot remember them.
  • The server can no longer call the client. Modern clients discard inbound requests, so questions are embedded in a result and the client re-sends the original request with the answer.
  • State that has to survive travels with the message. That is what requestState is for — there is nowhere on the server to put it.

Everything in this deck is one consequence or another of that removal — see the Flow Diagram for the shape it produces on the wire.
