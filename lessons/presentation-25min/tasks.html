A quick tour of the tasks extension — long work stops blocking, and the server decides when

The Idea in One Sentence

Instead of holding a JSON-RPC request open until the work completes, the server immediately replies with a task handle (resultType: "task") and runs the work in the background. The client polls tasks/get on its own schedule; once the status is terminal, that same poll carries the underlying result.

Now the server's decision. The old per-request params.task opt-in is gone, and servers MUST ignore it if one arrives. A handle may only be handed to a client that declared the tasks extension on the very request being answered — there is no session in which to remember it.

The Lifecycle

stateDiagram-v2 [*] --> working working --> input_required input_required --> working working --> completed working --> failed working --> cancelled completed --> [*] failed --> [*] cancelled --> [*]

Three terminal states. Receivers MUST NOT move a terminal task back to working. The input_required hop is the only reason tasks/update exists — it delivers inputResponses to a task that is waiting.

An Extension Now, Not Core

The top-level tasks capability slot is gone. Both sides declare the extension by identifier instead — and the client re-declares it on every request, because there is no handshake to declare it once.

Server, in server/discover

"capabilities": {
  "tools": { "listChanged": false },
  "extensions": {
    "io.modelcontextprotocol/tasks": {}
  }
}

Client, in every params._meta

"io.modelcontextprotocol/clientCapabilities": {
  "extensions": {
    "io.modelcontextprotocol/tasks": {}
  }
}

The Wire Flow

sequenceDiagram participant C as Client participant S as Server C->>S: tools/call (client declared the tasks extension) S-->>C: resultType: task { taskId, status: working, pollIntervalMs: 1000 } Note over S: Tool runs in background C->>S: tasks/get { taskId } S-->>C: resultType: complete { status: working } Note over S: Task completes S->>C: notifications/tasks (full task snapshot) C->>S: tasks/get { taskId } S-->>C: resultType: complete { status: completed, result }

The status notification is the bare notifications/tasks — the notifications/tasks/ prefix is reserved, so notifications/tasks/status is not a legal name. Its params are the whole task snapshot.

What Is Left, and What Went

MethodPurpose
tasks/getPoll status; carries result, error, or inputRequests as the status calls for
tasks/updateDeliver inputResponses to a task sitting in input_required
tasks/cancelBest-effort cancel (-32602 if already terminal)
notifications/tasksPush on every status change

Removed: tasks/result (clients poll tasks/get instead) and tasks/list (with no session to scope a listing to, it would leak other callers' task ids). Both now answer -32601. Renamed: ttl → ttlMs and pollInterval → pollIntervalMs.

A handle or a question, never both. resultType holds one value, so a tools/call answers either task or input_required. Commit to the shape before the tool works out what it is missing — answer a question to a task-declaring client and the Inspector rejects it with "Unsupported result type input_required for tools/call". A task asks later, as a status, through tasks/update.

Live Demo

  • Call key_word_search from a client declaring the tasks extension — the reply is a handle, not the answer. Nothing in the request asked for that.
  • Watch the Inspector poll tasks/get once a second with string ids inspector-ext-1, -2, -3… until status flips.
  • Then tasks/cancel the finished task for -32602 — terminal is terminal — and tasks/list for -32601.
