The Problem

Without MCP Apps

The tool returns 58 lines of path, keyword_count=N. The user reads a wall of text and cannot sort, filter, or click anything.

With MCP Apps

The same result renders as a sortable dashboard inside the chat — and the user can re-run the search from the panel itself.

No new methods. MCP Apps is tools/list and resources/read doing exactly what they already did — plus one metadata field.

Three Changes to the Server

1. Declare the extension in initialize

"experimental": { "io.modelcontextprotocol/apps": {} }

2. Point the tool at its UI via _meta

{
  "name": "key_word_search",
  "inputSchema": { ... },
  "_meta": {
    "ui": { "resourceUri": "ui://keyword-search/mcp-app.html" }
  }
}

3. Serve that URI as HTML with the app MIME type

ui://keyword-search/mcp-app.html
  → text/html;profile=mcp-app

In this codebase: AppTool, AppMeta, and UiMeta carry the metadata, AppToolBuilder.withResourceUri(...) wires it up, and resources/read special-cases the ui:// URI to return lesson/mcp-app.html.

What Happens at Runtime

1
Host calls tools/list and sees _meta.ui.resourceUri.
2
Host preloads the HTML with resources/read — before the tool is ever called.
3
User asks a question; host calls tools/call as normal.
4
Host renders the preloaded HTML in a sandboxed iframe and hands it the tool result over postMessage.
5
The panel can call the tool again — the user re-searches without typing a new prompt.

Security Model

The UI is untrusted content, so the host sandboxes it:

No direct network access
No access to the host page or DOM
No credentials or tokens

The only channel out is a controlled postMessage bridge — the app may request tool calls, but the host decides whether to run them.

Live Demo

  • resources/read it and show the returned MIME type text/html;profile=mcp-app.
