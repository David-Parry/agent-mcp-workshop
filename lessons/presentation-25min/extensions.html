Extensions in One Sentence

Anything beyond the core protocol lives under capabilities.extensions as a namespaced key. A peer that does not recognise the key simply ignores it — so new features ship without breaking old clients. (capabilities.experimental survives for non-standard, in-house capabilities.)

What this server declares

"extensions": {
  "io.modelcontextprotocol/ui": {
    "mimeTypes": ["text/html;profile=mcp-app"]
  },
  "io.modelcontextprotocol/tasks": {}
}

Identifier format

{vendor-prefix}/{extension-name}

  • Official: io.modelcontextprotocol/ui
  • Yours: com.acme/audit-trail

Clients declare theirs the same way, inside every request's _meta.

The Server Can No Longer Call You

On 2026-07-28 a server MUST NOT send a request to a client — modern clients silently discard inbound requests. That kills the three things servers used to ask for: roots/list, sampling/createMessage, and elicitation/create. All three survive as embedded requests; two of them, roots and sampling, are also deprecated under SEP‑2577, so this server builds only elicitation/create.

Multi Round-Trip Requests (MRTR): the server asks by answering. It replies resultType: "input_required" with the question embedded in the result; the client gathers the answers and re-sends the original request as a brand new request with a brand new id, carrying inputResponses and the requestState echoed back byte-exact.

An embedded request

"inputRequests": {
  "search_directory": {
    "method": "elicitation/create",
    "params": { "mode": "form" }
  }
}

A keyed map, not an array. Each entry has method plus optional params — and no jsonrpc, no id. Only those three methods may be embedded, and this server builds just this one. (params abbreviated; the full form is below.)

Why requestState exists

Sessions are gone, so the server has nowhere to remember what it was doing. The continuation travels to the client and back:

"requestState": "eyJrZXl3b3JkIjoicmVjb3JkIiwic3RhZ2UiOiJkaXJlY3RvcnkifQ"

  decodes to
  {"keyword":"record","stage":"directory"}

An opaque string to the client. This repo happens to base64 its JSON; the protocol only guarantees the exact bytes come back.

Elicitation — The One Question Left

The key_word_search tool needs a directory, and there are two ways it can get one. Pass arguments.directory and the call finishes in a single hop — that argument is the migration the specification names in place of the now-deprecated roots. Omit it — which is what a caller working from the tool description alone usually does — and the server has to ask, so it embeds a form.

1
tools/call arrives with no directory argument, so the server answers input_required embedding elicitation/create.
2
The client renders the form (mode: "form") and the user types a path.
3
Client re-sends tools/call with a new id, the same requestState, and the answer under inputResponses.search_directory.
4
Server decodes its own requestState, reads the directory out of the map, searches, and returns resultType: "complete". It never stored a thing.
5
Declined the form, or could not show one? The server stops asking and searches its own working directory — the call always returns a result, never a dead end.

There used to be a cheaper question ahead of that form: an embedded roots/list, which a client answers from its own configuration without troubling anyone, escalating to the form only when the roots came back empty. Roots is deprecated under SEP‑2577, so that stage is gone and the directory argument took its place. Deprecated is not removed, though — roots stays in the spec and works for at least twelve months, and real clients (the Inspector included) still declare "roots": {"listChanged": true} on every request. This server simply does not read the key.

Always leave a one-hop path. MRTR is optional for clients, and not every one implements it — the Inspector's own task-augmented tools/call path rejects input_required outright. A tool whose only route to an answer is a round trip is a tool those callers cannot use at all, so take the input as an optional argument and treat asking as the fallback.

The embedded elicitation

{
  "resultType": "input_required",
  "inputRequests": {
    "search_directory": {
      "method": "elicitation/create",
      "params": {
        "mode": "form",
        "message": "Pick a directory for the
           keyword-search tool to search in:",
        "requestedSchema": {
          "type": "object",
          "required": ["directory"],
          "properties": { "directory": {
            "type": "string",
            "title": "Search Directory" } }
        }
      }
    }
  },
  "requestState": "eyJrZXl3b3JkIjoi..."
}

New: mode is "form" or "url". Gone: the old elicitationId field — the retry correlates the answer now.

The answer, on the retry

{
  "method": "tools/call",
  "id": 3,
  "params": {
    "_meta": { ...envelope... },
    "name": "key_word_search",
    "arguments": { "keyword": "record" },
    "requestState": "eyJrZXl3b3JkIjoi...",
    "inputResponses": {
      "search_directory": {
        "action": "accept",
        "content": {
          "directory": "/Users/.../mcp/tools"
        }
      }
    }
  }
}

An input response is the bare result the method would have returned — nothing JSON-RPC-shaped. Three actions: accept, decline, cancel; only accept carries content.

Request IDs Are Strings or Numbers

With server-initiated requests gone, so is the reserved negative-id range that used to mark them. What replaced it is a subtler trap: the client picks the id, and it is not always a number. A server MUST echo it back in exactly the form it arrived.

RequestId as sent
server/discover"server-discover-probe-1"
subscriptions/listen"listen:0"
tasks/get (polling)"inspector-ext-1", "inspector-ext-2"…
everything else1, 2, 3…

This is why spec/RequestId.java and spec/RequestIdTypeAdapter.java exist. Before the migration id was a Long, and the very first message of the new revision crashed the server with NumberFormatException: For input string: "server-discover-probe-1".

Live Demo

  • Call key_word_search with a directory argument first — one request, one complete result. That is the baseline.
  • Drop the argument and call it again — now the reply is input_required, neither an answer nor an error.
  • Point at the requestState, then at the new id on the retry: two JSON-RPC exchanges, one logical call.
  • Decline the form and run it again — the search still returns, rooted at the server's working directory. There is no dead end to demo, by design.
